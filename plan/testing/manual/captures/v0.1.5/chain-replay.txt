# chain replay: sections 1 to 10 of the v0.1.5 walkthrough, in order, in one Model
# release: v0.1.5
# no model, no network, no key: canned messages and real key messages through the real Model
# canned: file names and texts, the replies, a one-file /diff, and the resumed transcript of section 10 (the live model's own items)
# section 4 is run in each of these orderings of the same inputs. The main path, which the chain goes on from, presses Shift+↑, g and PgDn after the README.md tool card finishes and before the reply's first text: the walkthrough says to press them "After the tool card finishes and before the reply's first text". In retry branch 1 the reply has started to stream (its first 100 lines have arrived) when the keys are pressed. In retry branch 2 the reply has finished, with the end of the turn, before the keys are pressed: the walkthrough's `reply finished first` case, which it says to write beside the step, if no indicator appears, before trying again with a longer prompt
# state per section: selection, gutter, key-hint row, mode, scroll, modal, size and glyphs, read from the Model
# the "selection" line is the item the gutter is on; "none" means no item is selected
# the "gutter" line gives the selected item's rows and the transcript window's rows: the gutter is drawn only when a row of the item is in the window
# the "hint row" line is the last row of the frame, or says there is none at that height
# section 10 resume: App.ResumeLastSession sends [tui.NoticeMsg tui.TranscriptLoadedMsg tui.SessionUsageMsg]; this replay sends [tui.NoticeMsg tui.TranscriptLoadedMsg]; not sent: [tui.SessionUsageMsg]
# the resumed items in section 10 are the live model's own, not what the app builds from a session log, so the offset recorded there is not evidence of what a real resume shows
# live turns send further messages the replay leaves out, among them a BudgetMsg before each turn and a UsageMsg and a SessionUsageMsg for each usage report
